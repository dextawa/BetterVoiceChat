# BetterVoiceChat (BVC) 设计文档

> 状态：已确认的方案，随实现推进持续更新。包名 `top.dext.bvc`，MIT 开源。

## 1. 目标

BVC 是给 BungeeCord / Velocity 群组服用的 Minecraft 语音插件，用来替代 Simple Voice Chat（SVC），解决它的这些问题：

| SVC 的问题 | BVC 的做法 |
|---|---|
| 基于 UDP，开放端口容易被 DDoS | 只用 TCP，和 MC 共用同一个端口，继承现有 CDN / 高防 |
| 不能禁麦 | 服务器端强制禁麦：单人、单个子服、全服，可定时 |
| 没有回放 | BC 端滚动录音，总容量上限 1GB |
| 没有举报 | `/vreport` 生成证据包（含附近回放），Web 面板审核 |
| 组队麦受地点限制 | 子服内组队麦不限距离 |
| 没有身份优先 | 优先级 + 自动压低他人音量 + 子服内广播 |
| 占额外端口 | 和 MC 共用端口 |
| 不能整服禁麦、不能联动 | BC 统一管理，提供 API 供 LiteBans 等插件对接（只留接口） |

## 2. 基本原则

1. **声音永远不跨子服**。BC 端只做统一封禁与管理；转发前再次检查说话人和听众在同一个子服。
2. **谁能听到谁，由子服判断**（范围、队伍、房间都在子服算）。BC 只按子服给的表查表转发，不做任何空间计算。
3. **语音模式和队伍都由服务器决定**，玩家不能切换。玩家只能调别人的音量、本地屏蔽、设置按键、在服务器允许时选择声控。
   - 组队麦的队伍只有两个来源：子服的计分板队伍，或子服上小游戏插件通过 API 设置的分组。**客户端和玩家都无法自己组队**，协议里也没有任何"客户端选队伍"的消息。
4. **只有一个 BC**。不做多 BC 集群。
5. **玩家需要装客户端 Mod 才有语音**。是否强制装 Mod 可配置，默认允许不装 Mod 进服（没有语音）。

## 3. 总体架构

```
              ┌──────────────────────── BC（Velocity / BungeeCord）────────────────────────┐
 客户端 Mod ──┤ 端口复用识别 → 鉴权 → 查表转发 → 禁麦检查 → 录音 → 举报 → Web 面板 → API  │
  (A 或 B)    └──────────────▲───────────────────────────────────────────────────────────┘
                             │ 插件消息 bvc:server / bvc:proxy（经由玩家的 MC 连接）
                    ┌────────┴────────┐
                    │  子服插件        │  判断模式、计算"谁能听到谁"、维护队伍与房间、小游戏 API
                    └─────────────────┘
```

- **客户端**负责采集、编码、播放、混音、3D 方位、按键说话。
- **BC** 只转发 Opus 包，不解码；同时负责禁麦、录音、举报、Web 面板。
- **子服**负责所有"判断"：当前模式、范围内有谁、队伍分组、房间、谁能说话。

## 4. 模块

| 模块 | Java | 说明 |
|---|---|---|
| `protocol` | 8 | 线上格式：包定义、编解码、加密工具。客户端、BC、子服共用 |
| `api` | 8 | 对外 API：禁麦、模式、房间、队伍、事件 |
| `proxy/common` | 17 | BC 核心：会话、鉴权、转发、禁麦、录音、举报、Web 后端、存储 |
| `proxy/velocity` | 17 | Velocity 适配：事件、指令、插件消息、网络管线注入 |
| `proxy/bungee` | 17 | BungeeCord 适配 |
| `backend/bukkit` | 8 | 子服插件：Spigot / Paper / Folia，1.8 到最新 |
| `client/core` | 8 | 客户端核心，不依赖 MC：网络、Opus、混音、抖动缓冲 |
| `client/mc/*` | 按版本 | 各 MC 版本 / 加载器的适配层，多版本构建（独立 Gradle 构建） |
| `web` | — | Web 面板前端（静态文件，打包进 BC 插件） |

BC 端最低 Java 17（Velocity 和 BungeeCord 本身都要求 17+）。子服插件和客户端核心编译为 Java 8 字节码，以支持 1.8 服务端和客户端。

## 5. 传输层

客户端到 BC 有两种传输方式，用同一套包格式：

- **A：独立 TCP 连接，同一端口**。客户端再开一条连接到 MC 的地址和端口。BC 在网络管线最前面放一个识别器，识别出 BVC 连接后接管，否则原样交给 MC 处理。语音不和区块数据抢同一条连接。
- **B：塞进 MC 连接**。语音作为插件消息（通道 `bvc:voice`）在 MC 连接里传。

### 5.1 选择与回退

- 服务器策略：`AUTO`（默认）、`A_ONLY`、`B_ONLY`。
- `AUTO` 下客户端先试 A，超时（默认 5 秒）或失败就退到 B。
- 客户端 Java 环境不支持所需的密钥交换算法时，直接用 B。

### 5.2 会话建立

1. 玩家进服后，客户端通过 `bvc:voice` 发 `Hello`（协议版本、Mod 版本、MC 版本、支持的传输方式）。
2. BC 回 `Welcome`：玩家的会话 ID、一次性令牌、传输策略、语音地址（空 = 和 MC 相同）。
3. 走 A：客户端建立新连接，先发一个"看起来合法的 MC 握手包"，服务器地址字段为 `<原地址>\0BVC\0<协议版本>`（和 Forge 在地址后加 `\0FML\0` 同一个思路）。随后发 `Auth`。
4. 走 B：客户端发 `SelectTransport(B)`，之后语音都走插件消息。
5. 没有在规定时间内收到 `Hello`：按配置踢出（附下载链接）或标记为无语音。

### 5.3 A 的识别

- 识别器放在子连接管线的最前面（如果开了 PROXY protocol，就放在它的解析器之后）。
- 平台原有的初始化照常执行，其他注入网络层的插件（ViaVersion、Geyser 等）不受影响。
- 读到第一个包：地址里带 `\0BVC\0` 就移除 MC 处理器、装上 BVC 处理器；否则识别器移除自己，把读到的字节原样交给后面，之后零开销。
- A 的后续数据沿用 MC 的 VarInt 长度前缀分帧。
- Velocity 通过替换 `ServerChannelInitializerHolder` 中的初始化器注入；BungeeCord 优先用官方的 Unsafe API，没有时用反射。

### 5.4 鉴权与加密（A）

- 令牌一次性、绑定会话、30 秒过期。
- `Auth` 不直接发令牌，而是发 `HMAC-SHA256(令牌, 客户端公钥)`，防止被窃听后冒用。
- 密钥交换用 ECDH（secp256r1，Java 8 自带），会话密钥由 ECDH 结果和令牌一起派生（HKDF-SHA256），每个方向一把。
- 之后整条流用 AES-128-CTR 加密（流加密，不增加每包开销）。
- 未鉴权的连接：限时 5 秒、限制并发数，超时或失败直接断开，不分配任何资源。
- B 直接用 MC 连接本身（正版服 MC 连接是加密的）。

### 5.5 插件通道

| 通道 | 方向 | 用途 |
|---|---|---|
| `bvc:voice` | 客户端 ↔ BC | 控制消息 + B 传输的语音 |
| `bvc:server` | 子服 → BC | 模式、房间、分组、邻居表、玩家标记 |
| `bvc:proxy` | BC → 子服 | 玩家 ID 绑定、语音状态、重新同步请求 |

通道名是带冒号的小写名字，在 1.8 和 1.13+ 都合法，ViaVersion 不会改名。BC 拦截这三个通道：客户端发来的 `bvc:server` / `bvc:proxy` 一律丢弃，子服发来的 `bvc:server` 不转给客户端。

## 6. 语音判定（子服负责）

### 6.1 模式

每个子服在自己的配置里定义默认模式；小游戏插件可以用 API 创建"房间"，每个房间有自己的模式。

| 模式 | 含义 |
|---|---|
| `PROXIMITY` 范围麦 | 同一世界、半径以内（半径可配） |
| `TEAM` 组队麦 | 只有同队的人互相听到，不限距离 |
| `FREE` 自由麦 | 房间（默认是整个子服）里所有人互相听到，没有距离限制 |
| `TEAM_PROXIMITY` | 队友不限距离，其他人按范围 |
| `DISABLED` | 这个子服 / 房间没有语音（比如登录服） |

说话方式也由服务器定：`ANY`（按键或声控）或 `PTT_ONLY`（只允许按键说话）。
注意：`PTT_ONLY` 只能在客户端执行，服务器无法区分按键还是声控；作弊客户端可绕过，靠禁麦和举报兜底。"谁能听到谁"则由服务器路由，改客户端绕不过。

### 6.2 子服上报给 BC 的数据

子服用 BC 分配的紧凑玩家 ID（VarInt）描述关系：

- **成员关系** `Membership{玩家, 房间ID, 分组ID}`：自由麦时分组 = 房间；组队麦时分组 = 队伍；0 表示无分组。队伍来源默认是计分板队伍，子服上的小游戏插件可以通过 API 覆盖（只有服务端能设置，客户端不能）。
- **邻居表** `Neighbors{玩家, [能听到他的人]}`：只在有范围语音时发送。子服用网格计算，只在集合变化时发送这个玩家的完整列表（幂等），每隔几秒全量重发一次用于自愈。
- **玩家标记** `PlayerFlags{玩家, 优先级, 能否说话, 能否听, 能否广播}`：例如观战者、死亡玩家。
- **区域信息** `Zone{玩家, 模式, 说话方式, 半径, 房间名}`：BC 转给客户端用于界面显示。

计算频率默认每 2 tick（10 次/秒），在异步线程里基于主线程快照计算。

### 6.3 BC 的转发

对说话人 S 的每一帧：

1. 检查：S 已鉴权、在子服 X、未被禁麦（单人 / 子服 / 全服范围）、全服或子服整体禁麦未开启（或有绕过权限）、子服标记允许说话。
2. 听众集合：
   - 按住广播键且有广播权限 → S 所在房间的所有人；
   - 否则 → S 所在分组的成员 ∪ S 的邻居表。
3. 过滤：听众必须也在子服 X、已连上语音、没有关闭收听。
4. 每个听众同时最多收 N 路（默认 8），优先级高的优先。
5. 发给每个听众的包带上类别（分组 / 范围 / 广播）和优先级。
6. 交给录音器（异步追加写入）。

BC 端每帧的工作是几次哈希查找加 N 次缓冲区写入，不做空间计算。

### 6.4 3D 方位

- 只有"范围"类别的声音做 3D 方位和距离衰减；分组和广播的声音不衰减。
- 客户端优先用自己世界里该玩家实体的位置（最平滑）；实体不可见时（隐身、超出追踪距离），由子服补发坐标（后续里程碑）。

## 7. 优先级、广播、闪避

- 优先级 0–255：取 BC 权限 `bvc.priority.<n>` 和子服 API 给出的值中较大者。
- 高优先级的人说话时，客户端把低优先级的声音压低（分贝数由服务器下发）。
- 有 `bvc.broadcast` 权限的人按住广播键时，所在房间（默认整个子服）的人都能听到。不跨子服。

## 8. 禁麦

- 范围：全服（所有子服）或单个子服；可永久或定时；记录原因和操作者。
- 整体开关：全服禁麦、某个子服禁麦；有绕过权限的人（如管理员）不受影响。
- 执行点在 BC：被禁玩家的包直接丢弃，同时通知客户端显示"已被禁麦 + 剩余时间"，客户端停止发送以省流量。
- 指令（BC）：`/bvc mute <玩家> [子服|*] [时长] [原因]`、`/bvc unmute <玩家> [子服|*]`、`/bvc globalmute on|off`、`/bvc servermute <子服> on|off`。
- API：`MuteService`（mute / unmute / isMuted / 查询），监听器 `MuteListener`（禁麦、解禁、全服 / 子服开关变化）。子服插件也能通过 `bvc:server` 请求禁麦。
- 联动：**只留接口，不内置任何联动**。LiteBans 等插件由服主或第三方通过上面的 API 自行对接（例如在 LiteBans 禁言事件里调用 `MuteService.mute`）。

## 9. 录音

- 在 BC 端记录经过检查、实际被转发的每一帧，原样保存 Opus 数据，不转码，几乎不占 CPU。
- 只录真正在说话的片段（客户端按键 / 声控决定是否发送）。
- 文件：按 `日期/子服/小时` 分段的只追加文件，记录说话人、时间戳、序号、Opus 数据；每段话（一次按键或一次声控）在数据库里有一条索引，便于按玩家、时间、子服查找。
- 总容量上限 1GB（可配置），满了从最旧的分段开始删除。
- 估算：码率默认 16kbps（由服务器统一下发给所有客户端），每人说话一小时约 8MB，1GB 约 125 小时说话量。
- 为了还原"举报人当时听到的内容"，BC 为每个听众维护最近 N 分钟"听到过谁、什么时间段"的轻量记录。

## 10. 举报

- 玩家指令 `/vreport <玩家> [原因]`（别名可配，冷却时间可配）。
- 生成证据包：被举报人和举报人在前后 N 分钟（默认前 5 分钟）的发言，加上举报人这段时间听到的所有人的发言。
- 证据包把对应的帧复制到单独的文件里，不占 1GB 滚动空间，也不会被滚动删除；处理后按配置天数保留。
- 通知在线且有权限的管理员。

## 11. Web 面板

- 由 BC 插件内置（JDK 自带 HTTP 服务器），默认监听 `127.0.0.1:8790`，建议用 Nginx 反代，不占 CDN 端口。
- 登录：游戏内 `/bvc web` 获取一次性登录链接；权限 `bvc.web.review`、`bvc.web.mute`、`bvc.web.admin`。
- 功能：举报队列与处理；多轨回放（按举报人视角混音，可单独静音或独听某人，时间轴显示每段发言）；按玩家、时间、子服搜索录音；在面板里禁麦 / 解禁；审计日志（记录谁听了哪段录音、做了什么操作）。
- 播放：服务器把 Opus 帧封装成 Ogg Opus（只封装，不转码），浏览器用 Web Audio 按时间戳排程播放。

## 12. 客户端

- **核心**（Java 8，所有版本共用）：连接管理（A / B 回退）、Opus 编解码（纯 Java 的 Concentus）、声控检测、抖动缓冲（TCP 下自适应，过期帧丢弃）、混音、闪避、3D 计算。
- **音频后端**：OpenAL（1.8–1.12 为 LWJGL2，1.13+ 为 LWJGL3）。
- **适配层**（每个版本）：按键注册、HUD、设置界面、插件通道收发、读取视角与玩家实体位置。
- **按键**：按住说话（默认 V）、广播键（默认 B，只对有权限的人生效）、本地闭麦、关闭收听、打开设置。服务器允许时可选声控或按一下切换。
- **HUD**：麦克风状态（说话中 / 被禁麦 / 等待按键）、当前模式（例如"范围麦 48 格"）、正在说话的人。
- **客户端不提供**：组队、换语音模式、换房间。这些只显示服务器下发的结果。
- **版本**：首批 26.3 Fabric 和 1.8.9 Forge（验证两头），再逐步覆盖 1.12.2、1.16.5、1.18.2、1.19.x、1.20.x、1.21.x、26.x 的 Forge / Fabric / NeoForge。

## 13. 存储

- BC 端默认内置 H2 数据库（单文件），可选 MySQL / MariaDB。
- 表：禁麦记录、举报、证据包元数据、发言索引、审计日志。
- 目录：
  ```
  plugins/BetterVoiceChat/
    config.yml
    messages.yml
    data/            H2 数据库
    recordings/      滚动录音（1GB 上限）
    reports/         举报证据包
  ```

## 14. 安全

- 未鉴权的 A 连接限时、限并发，不分配资源。
- 客户端不能伪造 `bvc:server` / `bvc:proxy` 消息（BC 拦截）。
- 子服必须只能通过 BC 访问（群组服的常规要求）。后续可加子服与 BC 的共享密钥校验。
- 录音需要在服务器规则或进服提示中告知玩家。

## 16. 实现记录

写代码过程中确定下来的细节，供后续开发参考。

### 16.1 端口复用的注入点（已在真实服务端验证）

- **Velocity**：`VelocityServer.cm`（`ConnectionManager`）→ `getServerChannelInitializer()` 返回一个持有器，调用 `set()` 换成包装后的初始化器。原初始化器先执行，再把识别器放到最前面（Velocity 的 PROXY 协议解析器没有固定名字，按类名 `HAProxyMessageDecoder` 查找）。
- **BungeeCord**：官方接口 `ProxyServer.unsafe().setFrontendChannelInitializer(...)`；老版本或分支没有这个接口时，用 `sun.misc.Unsafe` 替换 `PipelineUtils.SERVER_CHILD`。
- 2026-11-05 在 Velocity 4.3.1、BungeeCord 26.1 上验证：同一端口上，普通的 MC 状态查询照常返回，BVC 握手被接管并返回鉴权结果。

### 16.2 编译目标

- Velocity 4.x 的 API 是 Java 25 字节码。BVC 编译时用 Velocity 3.4 的 API（Java 17，接口一致），同一个 jar 能在 Velocity 3.x 和 4.x 上运行。
- 事件优先级用 `priority`（`order` 已废弃）；插件消息监听设为 `async = false`，保证音频帧顺序、不经过事件线程池。

### 16.3 A 通道的握手顺序

1. 客户端：伪 MC 握手包 + `Auth{会话ID, 客户端公钥, HMAC(令牌, 公钥)}`，可以放在同一次发送里。
2. BC：校验后用**明文**回 `AuthResult{成功, 服务端公钥}`，随即在帧解码器前插入 AES-CTR。
3. 客户端收到 `AuthResult` 之前不能再发任何数据；之后双方全部加密。
4. 令牌一次性：校验失败也会作废，必须重新 `Hello` 获取。
5. BC 发往客户端的包先进入每个连接的队列，每个事件循环批量写入、只 flush 一次；慢客户端积压超过 512 个包时直接丢弃新包（过期的语音没有意义）。

### 16.4 子服表的乱序保护与重启

子服发来的 `Membership`、`Neighbors`、`PlayerFlags`、`ZoneInfo` 都带一个递增序号，BC 对每个玩家、每张表记住已应用的最大序号，更旧的直接忽略。子服插件用"启动时间（毫秒）× 1000"作为初始序号，所以重启后的序号也比旧实例大。

BC 和子服各有一个每次启动随机生成的实例 ID，放在 `ProxyHello` / `BackendHello` 里：
- BC 每次玩家进入子服都会发 `ProxyHello`。子服只在第一次见到某个 BC 实例时回 `BackendHello` 并全量重发，所以 BC 重启后子服会自动重新同步。
- BC 只在子服实例 ID 变化（子服重启）时清空该子服的表；同一个子服实例重复打招呼不会清表。

### 16.5 构建环境备注

在某些 Windows 机器上（临时目录路径带 8.3 短名时），Java 的 NIO 无法创建 Unix 域套接字，Gradle 会报 `Unable to establish loopback connection`。解决办法是给 JVM 指定一个短路径：`JAVA_TOOL_OPTIONS=-Djdk.net.unixdomain.tmpdir=D:/tmp/uds`。

### 16.6 子服插件的实现

- **区域的确定顺序**：插件 API 的房间 → 配置里的世界（`worlds:`）→ 子服默认区域。每个区域是一个独立"房间"（隔离 + 广播范围），默认区域是房间 0。
- **分组**：自由麦 = 整个房间一组；组队模式 = 队伍一组（API 设置的分组优先，其次是玩家自己计分板上的队伍，再其次是主计分板）；没有队伍的人在组队麦里谁也听不到。
- **范围**：只在范围类模式里计算；同房间、同世界、三维距离 ≤ 半径；用格子大小 = 半径的网格，每人只查 27 个格子；同队的人不重复放进邻居表。
- **旁观者**：`SAME` 和普通人一样；`LISTEN_ONLY` 能听不能说；`SEPARATE` 放进一个单独的自由麦房间，只和其他旁观者互相听到。
- **线程**：采样（位置、队伍、权限）在拥有该玩家的线程上做，Spigot/Paper 是主线程（每 2 tick 一次，只读几个字段），Folia 是玩家所在区域线程（每个玩家一个实体任务）。计算在独立的 `BVC-Planner` 线程上做，不占游戏线程。权限每 5 秒才重新检查一次。
- **发送**：只发生变化的条目，每 5 秒全量重发一次用于自愈；单个包不超过 30000 字节（Bukkit 1.8 的插件消息上限是 32766）。插件消息借在线玩家的连接发，优先选 BC 注册过 `bvc:server` 通道的连接。
- **Folia**：调度器代码放在单独的源码集里，按 Java 17 和 Paper API 编译，只在检测到 Folia 时通过反射加载；其余代码是 Java 8 字节码，能在 1.8 服务端上加载。Folia 上读取计分板可能失败，失败时只警告一次，改用 API 设置分组。
- **管理命令** `/bvcs`：`info`（BC 连接、计算耗时）、`player <名字>`（采样位置、区域、分组、范围内的人、权限）、`rooms`、`reload`。
- 玩家离开子服时，API 给他设置的覆盖项（房间、分组、优先级等）会被清除。

### 16.7 端到端测试（`tools/e2e`）

用真实的 Velocity 4.3.1 + Paper 1.21.4 和 mineflayer 机器人测试整条链路，2026-11-06 全部通过：
- 基础场景 13 项：两种传输、加密握手、子服下发区域、双向听到、帧顺序、结束包、心跳、不回声。
- 规则场景 18 项：范围内外（48 格边界两侧）、配置重载切换组队麦、计分板队伍、队伍不限距离、退队、自由麦、旁观者两种策略、下界单独设为自由麦。
- 测试过程中子服和 BC 都重启过多次，重新连接和重新同步都正常。

### 16.8 客户端的实现

- **客户端核心**（`client/core`，Java 8，不依赖 MC）：连接管理（先试 A，失败自动退到 B；断线后指数退避重连）、Opus（Concentus）、声控（带 300 毫秒拖尾）、每个说话人一个缓冲（先攒 2 帧再播，落后超过 10 帧直接跳到最新）、混音（距离衰减 + 左右声道定位 + 低优先级压低 + 限幅）、本地音量和屏蔽。音频设备用 Java Sound，1.8 到 26.x 都能用，不依赖 LWJGL 版本。
- **说话规则**：服务器下发的规则永远优先，包括禁麦、"不能说话"、"不开放语音"和"只允许按键说话"（这时声控和按一下开关都会变成按住说话）。广播键只有服务器允许时才生效。
- **测试**：客户端核心和 BC 核心在同一进程里联调（真实 TCP、真实加密、真实 Opus），覆盖两种传输、禁麦、立体声方位、断线重连、服务器没装 BVC。
- **新版本适配层**（`client/modern`，独立的 Gradle 构建）：Stonecutter 负责多版本 / 多加载器，所有节点共用一份源码，版本差异用 `//? if >=1.20.5` 这类注释条件切换。26.x 不再混淆，用 Architectury Loom 的 `loom-no-remap` 插件（普通的 `dev.architectury.loom` 会因为缺少映射表而失败）；26 以下的版本用 `dev.architectury.loom` 加 Mojang 官方映射，构建时自动重映射到 Fabric 的 intermediary 或 Forge 的 SRG 名字。目前的节点：1.20.1 Fabric / Forge，1.20.4 Fabric / NeoForge，1.20.6 Fabric / NeoForge，26.3 Fabric / NeoForge。每个加载器各自只有一个入口类。客户端核心、协议、Concentus 作为内嵌 jar 打进 Mod，玩家只需要装一个文件（Fabric 版另需 Fabric API）。构建只需要 JDK 21：Java 17 的目标用 `--release 17` 编译。
- **26.3 的 API 变化**（已处理）：HUD 绘制改为 `GuiGraphicsExtractor`；按键分类改为 `KeyMapping.Category`；自定义网络包必须注册 `CustomPacketPayload` 类型；NeoForge 的网络包注册设为 `optional()`，没装 BVC 的服务器也能正常进入。
- **1.20.x 的 API 差异**（已处理）：`ResourceLocation` 代替 `Identifier`，`GuiGraphics.drawString` 代替 `text`，按键分类是普通字符串。1.20.5 之前没有 `CustomPacketPayload.Type` 和 `StreamCodec`：Fabric 用旧的频道 API（`ResourceLocation` + `FriendlyByteBuf`），NeoForge 20.4 用 `RegisterPayloadHandlerEvent`，Forge 1.20.1 用 `EventNetworkChannel`（两端的版本校验都允许对方没装）。这几种旧 API 的回调在网络线程上执行，所以先拷出字节，再切到游戏线程交给客户端核心。Forge 和 NeoForge 20.4 读取 `META-INF/mods.toml`，构建时会把 `neoforge.mods.toml` 改名；所有 Forge 系的版本都设置了 `displayTest = "IGNORE_ALL_VERSION"`，服务器列表不会因为服务器没装这个 Mod 而显示不兼容。
